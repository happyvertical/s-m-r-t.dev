# s-m-r-t

> s-m-r-t is an MIT-licensed TypeScript stack for agentic software that people and agents use through the same screens, rules and permissions. Describe a record once and the storage, forms, API, command line and agent tools are generated from it. The site has three doors, BUILD, FEATURES and DOCS. FEATURES groups what ships into nine sections (Agents, Basics, Screens, Content, Messaging, Commerce, Operations, Marketing and World), and each feature has a showcase with a live example where the packages ship one. build-a-boilerplate, behind BUILD, assembles a working mock-up for a kind of business in the browser and exports the plan as a file. DOCS holds every technical page, for developers and for agents.

## Released boundaries

This site documents the installed s-m-r-t release. The framework supports a shared domain model and manifest. It generates REST, CLI, MCP, and selected WebMCP surfaces. Agent-assisted form controls support explain, validate, staged-change, and confirmed-apply flows. Application MCP surfaces include allow-lists and policy checks. These explicit surfaces do not expose every model method or field.

Generated runtime operations still resolve through the application’s principal, tenant scope, field policy, writable-field rules, permissions, and any required confirmation. Development MCP is a separate, read-only development plane; it never executes the project’s application entry and never reads record payloads, principals, or credentials. Awareness is not authority: discovery never grants permission.

## Runtime provenance in the development MCP: read-only and only when configured

Without a development database configured, the development MCP answers from the workspace and installed packages only. With one configured (SMRT_DEV_DB_URL or the project’s CLI database setting), it adds read-only runtime provenance: migration, job, schedule and dispatch health from the framework’s system tables, a tail of the change feed, and a sanitized snapshot of the booted object registry. That snapshot is built from manifests without executing the project’s application entry. Payloads, results, agent configuration and credentials are never read. These tools distinguish observed facts from declared facts. Live data operations remain on the generated and application MCP runtime plane and remain policy-controlled.
